# D1 Max 单楼层执行闭环：实现与验收记录

## 历史结论（09-27；10-03 更新见文末）

本轮建立了正式运行图，不是把旧预览的开关置为可运动。使用 09-23 地图的一楼原坐标子图；通信维持 Zenoh。真实组件、控制驱动替身已完成短路线到达及停稳，并通过六项安装包图级测试；长窗口和完整异常矩阵另列证据，不与短路线混算。**未连接真实 SDK、未启动生产导航、未让机器人运动、未自动部署或 push。软件隔离测试不等于实机验收。**

版本证据、输入哈希、会话参数及日志保存在 `experiments/single_floor_execution_20260927/`。最初冻结清单为 `before_inventory.json`，对应源码副本为 `before_sources.tar.gz`。原有未提交改动没有回退或覆盖。

## 运行职责与合同

正式入口为 `python3 -m d1max_pct_scan.single_floor_session`，依次提供 `prepare`、`seal`、`verify`、`run`；`view` 独立启动显示层。准备不连接 SDK，运行前核对生成消息、Python 导入文件、二进制、地图及参数哈希。混入生产旧二进制或修改已封存参数会拒绝启动，不能只复制一个 Python 文件后声称整套已部署。

| 层 | 当前实现与责任 |
|---|---|
| 唯一任务所有者 | BehaviorTree.CPP Navigator；一次固定路线、预览确认、许可、恢复、取消、到达和停稳 |
| 全局规划 | 常驻原生 PCT worker；原坐标一楼多 slice，完整路线另做硬约束和源支撑校验 |
| 局部参考 | `continuous_reference_node`，使用原始 NavigationState 同时间 local/global 状态建立坐标锚；版本化准备与回执 |
| 局部环境 / 求解 | 生产 GridMap、生产 SCAN；独占地图写入、固定快照池、独立验证和单求解 worker |
| 轨迹提交 | Native validation → tracker admission → BT geometry commit；新候选不是当前轨迹 |
| 跟踪 | odom 下实测进度；保持速度限制器；只允许前进与转向 |
| 独立门控 | 类型化 MotionDemand，绑定许可、曲线、原生碰撞证明及实际收到的双雷达源时间 |
| 唯一 SDK 写者 | 同一 Monitor 会话内的 v3 执行适配器；与旧 navigation_control 写者互斥 |
| 显示 | 两套 RViz 布局、同一个独立显示进程组；关闭显示不取消 BT 任务 |

`ExecutionVersion` 把任务身份与参考、坐标锚等执行版本分开。`ExecutionPermit`、`TrajectoryValidation`、`TrajectoryAdmission`、`MotionDemand`、`StopReport` 都有明确绑定与源时；显示 Path、裸 Twist、JSON 状态不具有运动授权。

已提交轨迹保留固定 odom 几何。新候选失败不清除旧曲线；但旧证明失效立即停止非零发送。普通定位校正不建立新任务，也不平移当前曲线。显式重新初值、失权或 SDK 重连不能复活旧授权。

## 地图和传感器输入

- 原始地图保持不变；新子图保留源点索引和原 XYZ，不压平地面、不假造非刚性逆 TF。
- 一楼不是单个 PCT slice。楼梯入口明确排除；缺地面或缺净空保持不通过，不用采集轨迹刷成自由空间。
- 全局 map；局部参考、逐束投影、GridMap、SCAN、跟踪和碰撞检查统一 odom。
- `NavigationState` 是同时间的原子状态输入；前后雷达保留真实来源、源时和射线原点。安全链不订阅 LIO 筛选点云，不继承旧预览近身清空框。
- 未观测、已观测但证据不足、确定占据不混淆。独立门控要求实际收到并已积分的扫描起始水位，不能拿扫描结束时间冒充积分证据。

### 原坐标地图与 PCT 的实际结果

默认候选是独立的 `source_identity_floor1_res015_candidate`，原跨层地图和第一版 0.10 m 子图均保留。新子图从 1,078,761 个源点中选取 1,005,042 个点，支撑点 118,438 个；保留原始 XYZ 和源点索引，一楼使用多个 slice，楼梯入口另行排除。0.15 m 是**全局搜索**分辨率；实时 GridMap 仍是 0.05 m，两者不是同一个参数。

原生 A* 修复了对角穿角、跨层分支提前丢弃、同高度不同层被 closed set 混为一格，以及高代价格被 gateway 条件放行的问题。原生 GPMP 在该原图上仍有硬约束失败，因此没有偷偷改成“GPMP 成功”；新配置显式选用 `native_astar_checked_smooth`：原生 A* → 可见性简化与五次平滑 → 源支撑高度 → 完整障碍、净空和源地面检查。未知净空拒绝，不凭轨迹补自由空间。

严格条件下 6 条正向路线各重复 3 次，共 **18/18** 通过；6 条反向路线 **6/6** 通过。正向长路线约 0.211–1.547 s，反向约 0.238–2.318 s，原生搜索本身约 12–33 ms。这里是算法与路线构建耗时，**不是完整 ROS 请求 P95，也没有达到所有请求 2 s 内的证明**。输入、策略、逐条结果见 `map/PCT_SOURCE_IDENTITY_EVIDENCE.md` 和对应 JSON。

随后补做了真实 `ComputeRoute` Action 端到端基准，使用相同 6 条查询各 3 次。优化前 18/18 成功，P50/P95/最大为 809/2155/2459 ms；查明提交完路线仍等待 500 ms 周期状态发布。改为全部提交状态写入后立即通知、保留原身份核验与周期心跳，再跑 18/18 成功且路线哈希不变，P50/P95/最大为 693/2026/2107 ms。**P95 仍略高于 2 s，不能写成已达标。** 原生 A* 只占约 27 ms 中位数，平滑、原图验证、消息编解码及 Action 返回必须计入。详细分解见 `action_benchmark_02/REPORT.md`。

最终安装态复测 `action_benchmark_03_packaged`（清空源码路径，从 `/tmp` 使用 copy-install）为 18/18、P50/P95/最大 668/2029/2034 ms。继续移除 Action 完成后的额外定时轮询等待，并缓存已经校验的不可变候选，避免重复解码整条路线；仍保留来源、身份、取消与 worker 退役核验。`action_benchmark_04_reactive` 同 18 个输入全部成功、各路线哈希一致，P50/P95/最大 **591/1921/1938 ms**。本组热启动端到端满足 P95 ≤2 s；18 个样本只是本组测量，不是 CPU 压力、NUC 或统计上可靠的尾延迟保证。

## 暂停和停止

短期碰撞证明到期只禁止非零速度，不能等同永久 SDK 失权。真正的任务所有者心跳丢失、撤销、SDK 失权仍触发不可自动恢复的停止过程。证明源时没有被延长。

停止分开表达：非零阻断、零指令提交、旧工作退役、源时可信的实测停稳。正常 HOLD 的历史零 ACK 不能充当稍后停止请求的 ACK；拿不到停止后采集的 MC 证据就报告停止未确认。到达还要在停稳后用新的 NavigationState 重新核对 XYZ 和可选朝向，不把曲线耗尽当成功。

真实执行入口要求可核对的物理验收记录：对应机器人/SDK 版本、标定与机器人几何哈希，以及几何、速度、制动、MC 时序、原始射线五类记录的文件哈希。低于默认 0.3 m/s / 0.5 rad/s 的实测上限会同时约束求解、跟踪、门控与 SDK。没有这些记录不能靠手动布尔标志开通。

这几次短路线结果不是长走廊性能 P95，不是动态绕障或实机通过。

graph06 原生曲线验证 2,142 次，P50/P95/P99/最大约 7.52/12.65/15.55/23.78 ms；验证时最老雷达源龄 P95 约 467 ms，接近 500 ms 限制，不能把它说成已满足充分实时余量。后续实际命令的安全证明必须保留真实源龄。

graph07 的全部 656 条曲线证明均为 `observed_free`。106 次短停中，88 次已经收到更新的有效证明，却被旧许可中绑定的旧证明及其截止时间阻断；另 18 次确有新鲜证据空档。每次短停又重置速度爬升，形成 200 ms 周期停走。修复采用**授权与安全证明分离**：BT 租约只表达同一已提交曲线的任务授权；其中证明序号是最低版本门槛。实际指令仍绑定一条具体的新鲜曲线证明和具体速度扫掠证明，沿用它们原始有效期；新的 invalid 立即阻断旧证明。没有延长传感器 TTL、放开未知空间或放宽新候选接入距离。

停止合同也区分了任务身份与执行版本：最后 StopReport 覆盖完整 execution/control/SDK/arm 和稳定任务身份，不因正常换参考窗、换坐标锚拒绝真正停稳结果。若停稳后又收到运动数据、MC 源中断或时钟代次改变，撤销当前停稳结论，必须重新取得连续一秒证据；历史零速度或旧停稳不能授权下一任务。

graph08 的实际控制扫掠检查 P50/P95/最大为 0.293/0.394/0.661 ms；指令产生到验证结束 P95 17.60 ms。曲线验证 P95 19.62 ms；雷达源龄 P95 460.80 ms，最大 504.10 ms，该超龄样本被正确拒绝，仍不能宣称感知有充足时延余量。短程改善不等于长走廊、动态绕障和一小时稳定性全部通过。

`suite_02` 全部使用安装产物、私有 Zenoh 和控制驱动替身。六项均通过各自终止条件，动作成功与预期安全失败分别记录：

上述六例在任务终止后新建显示订阅，均收到原来的已提交全局路线（点数、源时和几何哈希相同）。这是晚订阅的图级证据，不冒充完整 RViz GUI 重开人工验收。

保留 `suite_01/blocked` 危险失败，不能拿新测试覆盖它：障碍在高速前进时突然出现在安全包络前约 5–8 cm，已处于夹具反应/制动保护距离 20 cm 内。墙出现到零速约 422.5 ms，首次无效证据到零速约 17.5 ms；最终安全包络侵入 6.68 mm。因此这一输入**未通过无侵入要求**。正例把障碍放在实际保护距离外，证明的是有条件的停止，不是任何距离突然出现物体都可避免碰撞。

该旧用例同时暴露了执行后 HOLD 永久等待；现增加 BT 单任务 30 s 受阻预算，短暂恢复不能刷新预算，连续稳定恢复才结束该次受阻过程。修复后 `suite_02/blocked_safe_distance` 已通过超时、停止和退役整图验证。

### 长窗口失败必须分开归因

`suite_03_windows` 的两例均未运动，不计通过。最初 +X 3.2 m 目标在原图中实际需要绕行，不能称为长直线。另一个已证明的输入缺陷是模拟房间扩到 ±6 m 后仍丢弃终点超过 8 m 的整条射线：首个近身未知格本有前后共 90 束穿过，却全部因远端距离 8.01–8.78 m 被删掉。GridMap 正常完整积分，未知格拒绝是正确行为。

修复只让模拟器保留实际房间终点，由生产 GridMap 裁剪边界并保持 no-hit 语义；不伪造 8 m 回波，不填自由格，不放宽生产未知策略。证据与被动重现见 `long_fixture_ray_diagnosis.json`、`.md`、`diagnose_long_fixture_rays.py`。后续长窗选用原图核验的 -Y 3.15 m 走廊，不覆盖这两次失败记录。

执行前也增加了唯一 BT 等待预算：定位 30 s、地图 15 s、参考 5 s、首条轨迹 20 s，一次准备/恢复累计最多 30 s。阶段跳变与重复反馈不续期，只有新的有效源时及稳定窗口才能重置。`suite_04_windows_obstacles/unobserved_start` 保留同一缺射线故障，12.54 s 后明确返回参考等待超时、软件退役确认；未确认执行、零运动，不伪造不必要的 SDK 实测停稳。其余四例在全局端点精确检查阶段失败，不能计为局部通过。

端点失败已精确定位：原生栅格 Y=6.595704650878908，冻结目标 Y=6.595704650878906。拼入目标后，1e-9 去重误删了最后冻结目标，保留相差 1.776e-15 m 的栅格点。修复只要求去重始终保留最后冻结端点，继续使用 `np.array_equal` 精确校验；篡改端点和障碍连接仍拒绝。同正式输入重新经过原生 PCT、平滑与源支撑检查：91 点、3.306 m、116 个支撑采样全部通过。

另将无解原因与安全证据分开：`waiting_observed_space` 是同一代求解尝试的原因事件，不会按碰撞证明的 0.4 s 截止误变成“参考未收到”。仅在任务、参考回执及待接纳代一致时保留原因，不更新其源时间，也不生成有效曲线或运动许可；仍受 BT 首轨迹 20 s/总等待预算约束。

`suite_05_windows_obstacles` 的长走廊与 +0.12 m 校正均到达并停稳，行程约 2.97/2.99 m、耗时 53.53/47.04 s，哈希一致。但直走廊运动阶段 43.2 s 中约 19.6 s 为零速，**不计流畅性通过**。静态箱体和运行中出现的箱体均在约 0.64 m 处被保护停住，65 s 内未完成绕行，保留失败。

针对这些结果的整改分工清晰：

- 感知：单调时钟已限制融合最多 5 Hz，却又要求采集时间前进至少 180 ms，产生第二次异步节流。改为到达 200 ms 融合间隔后接收两个确实比各自已积分水位新的完整观测；不修改原始源时、500 ms 有效期、重复数据拒绝或后雷达失效处理。
- 速度：原生限制三维速度模长，而控制器把水平速度直接设为 0.3 m/s 后仍有真实垂直速度。现在由已接纳曲线和支撑坡度派生水平速度/加速度预算；保留真实 `vz` 和原生三维上限，不扩大比较容差。
- 参考：正式窗口此前隐含默认 4 m，2 m 仅作用于原生规划 horizon。现显式统一为 2 m；已覆盖当前段终点时不再无意义重发，但真实坐标锚校正仍生成新候选。
- 绕障：原生局部目标选择此前只沿固定路线挑点，箱后未知时侧面通道没有被尝试。现在仅在原选择失败时，最多检查 40 个已观测侧前方临时目标；需要同版本原图支撑、正确楼层、实际 GridMap 的转向/通道验证，再走原生 A*/SCAN。全局路线不变，未知和缺支撑不放行。
- 上层：曲线可用、甚至零需求的碰撞证明有效，都不代表能前进。受阻监督增加精确匹配的实际非零需求证明与新鲜实测进展，不能用许可心跳或零命令刷新等待预算。

以上修改必须以后续整图结果验收，不能拿新增单元测试替代绕障成功。`suite_05` 的资源记录为 1 Hz 采样、自有导航进程加模拟传感器/机器人；长走廊采样 RSS 加总峰值约 2.42 GB（共享页会重复计数）、CPU 峰值约 2.77 核，不是 NUC 或一小时运行结果。

## 2026-10-03：开发版定位接入与系统合同整改

本节对应 `single_floor_execution_20261003_system_v2` 隔离候选，不把前文旧二进制的通过结果当作新版本验收。开发版全局重定位、连续局部状态和实时导航输出已一并 copy-install；没有启动生产服务、连接 SDK、改变实机授权、切换默认发布选择或 push。

### 按依赖顺序实施

1. **锁定实际入口和版本**：仍由 `single_floor_session` 生成会话，接口、BT、原生 SCAN、跟踪器、SDK、RViz、Python 应用和定位依赖使用同一候选的八个安装前缀。新消息与换轨合同预检阻止混用旧版本。源文件、安装文件、ELF、XML、地图与有效参数分别留证，源码改动不等于部署。
2. **先稳定定位合同**：开发版重定位沿真正的 BT 初始化阶段接入；索引建立和位姿确认使用分开的有限预算。50 Hz 因果预测与输出在一个定时回调中完成，同次目标时间在预测前确定。独立 `LocalNavigationState` 保留真实 posterior/IMU 源时、epoch 和 seed；短暂全局校正消息缺失不再带走连续局部控制状态，真实 LIO 重置仍撤权。
3. **统一参考与感知**：全局原坐标路线固定在 map；实时参考、原始双雷达逐束投影、生产 GridMap、SCAN 和跟踪均在连续 odom。新的 map→odom 锚只生成候选参考，不移动已经接纳的曲线，也不改变全局路线身份。自体删点与实体测量尚未验收，不以近身清空替代安全输入。
4. **再修调度和碰撞证据**：三槽地图快照有固定配额和独立读缓存；无槽是资源重试，不能误等到环境改变。实际速度扫掠、旧曲线续证和复核优先于候选入场检查；共用一轮期限，不给内部重试重新发一份预算。安全证明可以升级，但不能刷新原控制需求、机身状态或许可的时间。
5. **最后打通换轨与停止**：旧 active 曲线与新 prepared 曲线分槽。唯一 SDK writer 的精确 ACK 才改变已应用执行身份；ACK 区分软件提交、厂商调用结果与实测停稳。取消、迟到 ACK、发送失败和重连不能回滚到旧执行身份，也不能复活旧授权。

### 整图运行揭示的序号问题

最终换轨合同第一次运行 `closed_loop_handoff_normal_01` 在行进 0.314 m 后失败：新候选 356 到达时，旧曲线 357 已被 writer 接收。把两个角色共用一个递增水位，错误地将候选判为重放；后续 362/363、366/367 同样被拒，250 ms 的固定交接期限正确超时。其次，否定 ACK 漏带候选许可序号，而跟踪器同版本不同曲线的退休判断不够精确，导致安全旧曲线永久 HOLD。

修复针对实际顺序，而非放宽时效：grant 接收时冻结候选反重放下界，候选与旧曲线分别保持水位；成功 CAS 后以真正提交的候选建立 active 水位。否定 ACK 保留完整候选许可及曲线身份；只有确认“没有应用”且 commit 未前进的精确事实才释放候选，迟到的已应用事实仍保留新身份并 HOLD。坏 ACK、跨任务、过期、逆序和重复指令仍拒绝。

### 原生碰撞几何的同输入修复

实际地图以点对扩展体积查询碰撞时，需要反射上下不对称包络。旧实现把向下与向上的边界用反了，能将地面错算成机身障碍，也可能漏掉头顶障碍。探针使用生产 GridMap 查询和扫掠实现，配合明确标记的合成自由空间/平面夹具，验证软件几何合同；不是实机射线积分或自体测量。修成 lower = −upper、upper = −lower 后，地面 Z=0 的误阻塞消失，Z=0.1 的低障碍仍阻断，Z=0.96 的头顶危险由漏检变为阻断。没有增加删点框，也没有放开未知格。前后证据分别为 `experiments/local_planning_audit_20261002/envelope_contract_01/probe.json` 和候选内 `native/envelope_contract_after/probe.json`；实体轮腿包络仍需现场测量。

### 真实 rosbag：初始化通过，连续性未通过

`bt_bag_full_preview_final` 使用 09-23 凌晨跨楼层 bag 的原始前雷达、后雷达和前雷达 IMU，原 header/source 不改，不回放历史定位结果，不连接 SDK。开发版全局重定位被 BT 确认真正就绪，随后进入全局和局部阶段。中心 IMU 的外参和源时未证明，因此没有擅自替换进这次定位链。

240 s 回放的连续局部状态间隔 P50/P95/P99 为 20.01/22.60/38.82 ms，最大 420.43 ms。预测与输出回调计算 P95 为 8.45 ms、P99 为 13.07 ms、最大 25.98 ms。IMU header 最大间隔约 95 ms，但接收有聚簇和较长空窗；这是采集、回放调度及负载一起作用的证据，不能仅由 header 断言硬件损坏，也不能把回放延迟当作实机标定。

**50 Hz 配置已接通，不等于硬实时 20 ms 验收。** 该 bag 仍有不可用状态段，完整连续性结果为 false，局部阶段最终等待新鲜地图超时。系统保留真实不可用原因，不重发旧位姿伪造连续，不放大 IMU/预测 TTL 来凑通过。

### 发布与物理验收边界

候选与旧包分开保存。检查发现旧 `single_floor_execution_20261002_entry_v1` 的 seal 绑定了可变的定位源码；本轮源码替换后，旧包预检真实报告 `release_changed:…/navigation_output.py`。旧产物没有被覆盖，但不能称为当前已验证可直接运行的回退包。新候选必须冻结安装代码及源码副本，使用显式 `D1MAX_RELEASE`；不修改旧 seal 来掩盖差异。

物理阻塞项仍包括雷达测量原点/外参、轮腿与载荷包络、各姿态参考高度、SDK 速度比例、MC 时钟与延迟界限、制动与断指令停止。一小时持续运行和 NUC 资源验收未完成；单层软件改进不代表跨层运动能力通过。

### 初始入场与实际提交是三个不同事实

`closed_loop_schema2_correction_01` 暴露了真正的初始化断点：原生准备通过，不等于跟踪器安装成功，更不等于 SDK 已应用。首次 curve1/proof2 的准备仍有效时，上层发出许可，但跟踪器对实际位置的再次接入核对拒绝了曲线。上层却把提交意图记作已安装，之后继续给 curve1 升级证明版本，忽略后来 curve2–8 的新鲜成功准备。这次运行没有收到运动需求或 SDK 首次提交 ACK，机器人替身行程为零，最终按 30 秒受阻预算退出；不能把它归因于 SDK 或声称已闭环。

整改不放宽 1.25 cm / 0.05 m/s 接入条件，而是增加类型化 `TrackerGeometryReceipt`：准备回执、真实软件安装回执、唯一 writer 实际应用 ACK 独立记录。软件安装回执保留原许可、准备、原生证明和固定安装时间，心跳只携带新的原始机身采集时间，不能续写安装事实或借旧证明延长权限。未安装时允许同一路线重新选择新鲜候选；真正 writer 提交后不能被较新的“期望曲线”覆盖。迟到 ACK 只能确认既成事实，过期时 HOLD，不能恢复旧运动许可。候选、原曲线和实际应用序号分别反重放，缓存有界。

### 原始 IMU 的接收时钟与因果消费

对同一 09-23 bag 的 SQLite 原始录制时间和 IMU header 逐条核对：46,627 条前雷达 IMU 中，11,368 条映射后的源时间领先录制接收时间超过 10 ms，最大约 44.3 ms，没有超过 50 ms。输入时钟允许 50 ms 接收窗口，而旧预测器仅允许 10 ms 入队，形成软件合同不一致。录包中的接收聚簇和最长约 680 ms 空窗仍真实存在，不能因此断言全部缺失都是硬件原因，也不能断言所有 `imu_rejected` 均来自该差异。

修复将开发版因果预测器的接收窗口明确设为 50 ms：只允许进入有界队列，**绝不提前使用未来样本**；每次输出仍仅消费源时间不晚于目标时刻的样本。原 header、录制接收时间、源龄、预测上限和安全 TTL 不改。超过窗口、乱序、重放及重置保持拒绝。原 CDR 回归验证“可暂存”与“可用于当前预测”分开；完整回放结果另列，不能以单元通过代替连续性验收。

### 同一真实录包的定位对照与剩余缺项

### 任务连续性与即时控制证据分层

真实录包暴露了另一个时序放大：原始局部状态在发布时可用，20 Hz 消费和 10 Hz BT 的相位又使部分 IMU 源龄刚超过 100 ms；即时运动闸应 HOLD，但此前还把每次短暂 HOLD 当作任务阶段丢失，需要重新等待 0.6 s / 三个新样本。这混淆了持续任务与一条速度命令的许可。

整改保留原输入入场校验和 100 ms 即时 IMU 闸，任务工作流另检查实际收到的 typed LocalNavigationState、原始 source/receipt、后验传播边界和 epoch/seed。普通消费者相位过期可保留固定路线及参考工作流；Owner、跟踪器、安全门和 SDK 仍按即时证据阻断运动。真正 producer `usable=false`、硬重置或传播边界耗尽仍暂停/撤权，不重发旧位姿，不用任务能力替代运动能力。重复和逆序源时不能续期。

### 冻结依赖不等于重新标定或部署

新增 `localization_dependencies` 前缀按相同字节复制实际 Faster-LIO/Livox 运行依赖，解除旧绝对 build 目录的符号链接依赖；这是运行依赖冻结，不是重新编译或精度改善。七个会话模板从候选内 `source_snapshot` 读取，不再悄悄读取工作区的可变配置。ROS、系统库、PCT 外部 GTSAM/Metis 和原始地图仍有外部依赖，清单逐项记录，不能称为可随意搬机的自包含包。最终 seal 只用于版本一致性检查，`activation=false / physical_acceptance=false`，不会切换默认入口或恢复运动授权。

### 连续换轨的整图证据与工程整改

`closed_loop_receipt3_correction_01` 首次完整经过真实 BT、原生 PCT/GridMap/SCAN、跟踪器、安全门和 SDK 模拟唯一 writer，控制输出实际驱动替身机器人：21.53 s 内走行约 3.00 m，以最高约 0.297 m/s 到达并确认模拟停稳。累计 12 cm 普通地图校正后，全局路线哈希保持唯一。该结果不是实机、不是 rosbag 导航成功，也没有物理停止验收。

这次成功仍有四段行进中零输出，观察总长 1.155 s、最长约 1 s，不能称为流畅性通过。追查原事件而非修改限值后，确认以下断点：

- 精确新入场/全曲线证明到齐后，只剩约 31 ms 原期限；10 Hz Owner 定时器错过配对，下一次处理已过期。改为有界事件驱动配对，仍复用原签名许可，不增加期限。
- 原 worker 的入场源已过期，即使当前同曲线的新原生证明有效，也不能借旧入场宣称可接入。新的入场观测必须绑定最新真实 LocalState、原曲线域和实际 XYZ/速度，独立保留旧 TaggedBspline 源时作诊断。
- 旧策略用全曲线未来最低弯道限速限制当前入场，导致远处可提前制动的弯道也拒绝新候选。改为沿实际空间距离反向传播的制动速度包络；当前位置速度仍受约束，1.25 cm / 0.05 m/s 入场界限不放宽，正常换轨保留限速器历史。
- 位置异常推进到正常减速度无法满足的空间速度上限时，不能在限速器后硬裁剪然后宣称平滑控制。该情况应明确进入运动 HOLD，保留真实已安装曲线及实际 writer 身份，重新取得停稳和接入证据后恢复；不以正常地图校正或一条新 positive proof 清除该故障。

上面是同一成功但不流畅运行的根因，不是最终新版验收结论。最终回归须另列完整产物、失败反例和不可验证项；SDK ACK、软件安装与实际停稳依然分别表达。
