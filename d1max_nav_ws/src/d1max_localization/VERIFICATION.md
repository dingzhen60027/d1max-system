## 原因与修改

- 实机会话 `49655ff054bd40769f175f19e3f6a0b7` 的 LIO 遇到约 64.999 ms IMU 时间戳间隔，超过 50 ms 上限后永久锁定；输入适配器也记录了相同量级间隔。不能据此区分机器人发布端和传输端丢帧。
- 当时 SDK MC 正常约 50 Hz，机头状态为 1；这次持续故障不是 MC 缺失，也不是尾部前向导致。
- 保留 50 ms 上限，不补 IMU、不跨超限缺口积分。仅 IMU 缺口 / 覆盖起点缺失允许重新初始化；默认滚动 60 秒最多 3 次，超出预算停止。
- 重新初始化清空滤波器、积分历史和内存局部地图，重新收集初始化样本。只清理内存估计状态，不改用户 PCD / PGM。
- 局部里程计与失效事件改用带 `epoch` 的同一有序内部消息流，避免状态与数据跨话题到达顺序导致旧位姿误用。
- 新轮次撤销旧地图关系、旧初值、旧轨迹；忽略旧轮次结果和重置前排队的初值。恢复局部里程计不自动恢复全局定位，必须重新画初值并通过至少 3 次连续匹配确认。
- 时钟回跳、滤波异常和局部位姿跳变仍锁定。Web 直接展示具体原因、IMU 间隔 / 上限、恢复状态；严重局部故障不会被前端“恢复中”掩盖。
- 头尾模式保护保留，未自动切换机器人模式，也未擅自改变其坐标解释。所有恢复参数仍在唯一 `config/localization.yaml`，下次启动复制到新会话。
