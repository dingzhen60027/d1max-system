# D1 Max 中心 IMU 离线数据质量检查

## 结论

中心 IMU 是值得进一步接入验证的候选，但当前记录还不能认定为“高质量、连续 200 Hz 的独立新测量”，更不能直接证明车规级精度。

优点是本包长时间缺口比雷达 IMU 少，起始低动态段波动较小，角运动响应与另两只 IMU 一致。主要风险是六轴重复值、原始加速度尺度与 ROS 标准不一致、无有效姿态输出、协方差未知，以及外参和时间关系未确认。

**此中心 IMU 不是本次已有 Faster-LIO 原始地图的实际输入。** 19:01 建图运行保存的 `config/dual_lidar.yaml` 第 7 行选择的是 `/front_lidar/imu`。因此不能用中心 IMU 的问题直接解释该地图下沉，也不能保证换成它就解决下沉。

## 数据与方法

- Bag：`/home/dndx/d1max_nav_ws/bags/slam_raw_20260917_171716_fe8f38`
- 中心话题：`/imu_driver/imu_central`，frame 为 `imu_link`。
- 对照：`/front_lidar/imu`、`/rear_lidar/imu`。
- 读取全部三个 SQLite 分片，仅以 `mode=ro` / `query_only` 查询并反序列化。没有启动 ROS、回放、连接实机或修改生产配置。
- 统计单位为一条原始 IMU 消息。header 时间与录包时间保留为独立 int64 纳秒数组。
- 有效平均频率 = `(消息数−1) / 首末 header 时间差`，不是硬件标称采样率。
- 缺口以相邻 header 差值计算；不能仅凭 bag 判断缺口发生在传感器、驱动、传输还是录包端。
- 原始包中没有 MC 速度、独立静止标签、温度或运动真值；不做长期零偏/Allan 噪声定标。

中心流确实较少出现大于 50 ms 的长间隔，但仍有 448 次大于 30 ms 的间隔，不能称为连续无缺口。三个流均无 header 倒退/重复、NaN 或 Inf。中心数据无全零加速度/角速度样本。

接收时间存在批量到达现象。机器人 header 与 PC 录包时间有不同时间基准，不能把两者直接相减当作物理延迟；也不能用录包接收间隔替代传感器采样间隔。

## 2. 六轴重复值：接入前重点核查

**发现事实，影响等级高，证据明确：** 中心流 192,970 个相邻消息对中有 18,410 对六轴数值完全相同，但 header 不同；比例 9.54%。这一现象贯穿全包，不只在开头出现。

- 最长连续 11 条相同，header 跨度 50.000148 ms。
- 合并相邻完全相同的六轴数据后，数值变化事件约 177.21 次/秒；**这不是已测得的硬件采样频率，也不是丢包率。**
- 重复可来自旧值重新发布、驱动更新与发布解耦、上游行为或量化。仅凭 bag 不能确定根因。
- 对 LIO 的风险：如果确为旧值重发，快速转动/振动时，新增时间戳不代表新的运动测量。重复值也会影响噪声统计与时序分析。
- 推荐核查原始驱动的数据帧序号、采样时间、接收时间及发布机制；不要未经验证就丢掉所有重复值或人为制造 200 Hz 数据。

原始 SQLite 独立复核了最长重复段：`*_1.db3` 中 ID 为 50812、50822、50827、50829、50830、50833、50836、50840、50845、50850、50854，header 为 1772316914410127754 至 1772316914460127902，六轴只有一组唯一值。不是本次提取器制造的重复。

## 3. 单位、轴向和姿态字段

**接入风险高，数值事实明确，单位/外参解释尚待确认：**

- 中心起始 2 秒加速度均值约 `[-0.002519, +0.009073, -0.999678]`，全程模长中位数 0.999753。
- 这与 **g 尺度**一致，而不是正常含重力加速度以 m/s² 输出时应有的约 9.81。ROS `sensor_msgs/Imu` 标准要求 m/s²。驱动源码未找到，因此“原始单位为 g”是强烈的数据推断，不是厂商接口确认。
- 原始加速度主要沿 −Z；前雷达起始向量主要沿 +Y。由此不能完整确定各轴方向或传感器间旋转，尤其不能确定 yaw。不能照搬前雷达的 Rx(+90°) 适配，也不能只把 Z 取反冒充完整标定。
- 全部 192,971 条中心姿态四元数都为 `[0,0,0,1]`，不是随运动更新的有效姿态。接入端不应融合该 orientation。
- 三项 covariance 全程为零。ROS 语义是“不知道协方差”，不是“测量没有误差”。应使用明确标定/合理配置的噪声模型，无姿态输出应按接口约定标记或在消费端禁用。
- SDK 文档的 m/s²/rad/s 单位不能直接套给本话题，因为没有证明两条数据路径相同。

## 4. 短时波动与运动响应

固定取起始 2 秒，不按“最安静”筛选窗口。该段呈低动态，但没有独立证据证明机器人绝对静止。下表为移除相邻六轴重复后 364 个变化事件的描述统计；不是厂家噪声密度，也不是长期零偏稳定性。

| 中心 IMU 原始量 | X | Y | Z |
|---|---:|---:|---:|
| 加速度标准差，原始单位 | 0.000480 | 0.000485 | 0.000599 |
| 角速度均值，原始单位 | −0.000711 | −0.000144 | +0.000764 |
| 角速度标准差，原始单位 | 0.000648 | 0.000656 | 0.000620 |

若加速度确为 g，以上轴标准差约 0.0047–0.0059 m/s²；若角速度确为 rad/s，以上轴标准差约 0.036–0.038°/s。所有单位换算均保留这一条件。

小波动是积极信号，但安装位置、带宽、驱动滤波及真实运动都会影响数值，不能据此认定中心硬件一定比雷达 IMU 更精确。第一段角速度均值也不能直接作为整包不变的陀螺零偏。

角速度模长不受固定坐标旋转影响，可用于跨传感器运动响应检查。按共同 header 时间轴比较，中心与前/后雷达动态高度相似；约 10 ms 的相对移位能提高相关性。这提示需核查采样时间定义或滤波相位差，**不构成可直接写入配置的时间标定值**。详细计算保留在 `signal_review.py/json`。

## 5. 外参与硬件身份仍未确认

供应商 URDF 包含 `IMU_ICM42688_LINK` 与 `IMU_LUA300C_LINK`，但未找到 `imu_link` 与这两个 link 的驱动映射。不能仅凭“机身中央”“车规级”或 CAD link 名就确认该话题对应哪一颗芯片，更不能把 CAD 名义位置当成实机标定。

用于 LIO 至少需要厘清：原始轴定义和单位、点云坐标系到中心 IMU 的刚体变换 R/t、数据采样时刻和 LiDAR 点时间之间的关系。静止重力只能提供部分旋转信息，不能解决 yaw、平移和时间偏移。

## 6. 下一步建议（本次未实施）

1. 优先核查中心 IMU 驱动的重复发布及时间戳语义，并确认单位、姿态字段有效性。
2. 固定一套明确的中心 IMU ↔ 前雷达坐标关系，再做带多轴转动/平移激励的时空标定验证。
3. 采集有独立静止确认的预热后静止记录；长时静止数据另用于噪声/零偏稳定性评估，不能拿当前走动包做同等替代。
4. 单前雷达、同一 bag、关闭回环做对照，分别使用前雷达 IMU 与正确适配后的中心 IMU。以地面倾角、沿程高度漂移和配准质量判断真实改善，不只比较频率。
